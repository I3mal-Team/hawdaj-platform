# TICKET — المشرف لا يستطيع الدخول ولا تصله كلمة المرور

> ملف مستقل موجّه لـ Claude في مستودع `hawdaj-api`. لا يحتاج أي سياق سابق.
> **اقرأ هذا الملف كاملًا، ثم اتبع سير العمل أدناه. توقّف عند بوابة الموافقة قبل تعديل أي كود.**

- **المستودع:** `hawdaj-api` (Laravel 8.12 — لوحة تحكم بحارس `web` + Spatie Permission)
- **النوع:** Bug + إعداد تشغيل · **الأولوية:** عالية · **الطبقة:** Backend فقط (لا علاقة للموبايل/الويب)

---

## 1) العَرَض (Symptom)
عند إنشاء مستخدم بدور "مشرف / supervisor" من لوحة التحكم:
- **لا تصله رسالة كلمة المرور بالبريد** → لا يستطيع تسجيل الدخول.
- **لا يظهر أي خطأ** في اللوحة عند الإنشاء (يبدو أن العملية نجحت).

## 2) السبب الجذري (مؤكّد بالكود — تحقّق منه أولًا)
الملف: `app/Http/Controllers/Dashboard/Users/UsersController.php` → دالة `store()`.
1. الكود يرسل كلمة المرور بالبريد فعلًا:
   ```php
   $data['password'] = $request->password; // plaintext للإيميل
   try {
       $user->notify(new userMailNotification($user, $data));
   } catch (\Exception $e) {
       // ← catch صامت: يبتلع أي فشل بلا تسجيل
   }
   ```
2. الإشعار `App\Notifications\dashboard\userMailNotification` **`implements ShouldQueue`**
   → الرسالة **مؤجَّلة في الطابور (queue)**. إذا لم يكن عامل الطابور يعمل، **لا تُرسَل إطلاقًا**. ← **السبب الأرجح.**
3. **catch صامت** → أي فشل في البريد غير مرئي للأدمن.
4. إعداد `MAIL_*` في `.env` على السيرفر غير مؤكّد (قد يكون SMTP غير مضبوط/خاطئ).

**ملاحظة:** إنشاء الحساب + `assignRole()` يعملان بشكل صحيح. المشكلة **فقط** في وصول كلمة المرور، ومنها يتعذّر الدخول.

## 3) سير العمل المطلوب (اتبعه بالترتيب)
1. **تحقّق** من الكود أعلاه (`UsersController@store` + `userMailNotification` + `config/queue.php` + `config/mail.php` + وجود `.env`).
2. **حلّل الأثر:** ما الذي يعطّله غياب الطابور؟ (كل الإشعارات المؤجَّلة، ليس هذا فقط). هل هناك `failed_jobs`؟
3. **اقترح خطة (خيار أو اثنين)** — ملفات + خطوات + مخاطر + تعقيد.
4. **⛔ توقّف — انتظر موافقة صريحة قبل تعديل أي كود.**
5. نفّذ المعتمَد + اكتب اختبارًا (القسم 5).
6. راجعة ذاتية + شغّل الاختبار.
7. حدّث التوثيق (إن وُجد).

## 4) المطلوب إصلاحه
**(أ) تشغيل/إعداد — خارج الكود:**
- تأكّد أن عامل الطابور يعمل دائمًا: `php artisan queue:work` عبر Supervisor/systemd. افحص جدولَي `jobs` و`failed_jobs`.
- اضبط `MAIL_*` في `.env` واختبر إرسال بريد فعلي.

**(ب) كود:**
- **لا تبتلع استثناء البريد صامتًا** — سجّله (`Log::error(...)` مع رسالة واضحة) واعرض تنبيهًا للأدمن بأن المستخدم أُنشئ لكن إرسال البريد فشل (flash message).
- (اختياري مُستحسن) اعرض/انسخ كلمة المرور المؤقتة للأدمن في اللوحة بعد الإنشاء كخطة بديلة لا تعتمد على البريد.
- لا تغيّر منطق إنشاء المستخدم أو إسناد الدور (يعملان صح).

## 5) الاختبار المطلوب (إلزامي)
اكتب **Feature test** يغطّي:
1. `test_admin_can_create_supervisor_and_notification_is_queued`
   - سجّل دخول أدمن يملك `permission:create-user`.
   - `Notification::fake();`
   - POST لمسار إنشاء المستخدم ببيانات صحيحة + دور supervisor.
   - تأكيد: المستخدم أُنشئ في DB + أُسند له دور `supervisor` + `Notification::assertSentTo($user, userMailNotification::class)`.
2. `test_user_create_still_succeeds_when_mail_fails`
   - محاكاة فشل البريد → المستخدم يبقى مُنشأ + يُسجَّل الخطأ (لا ابتلاع صامت) + تظهر رسالة تنبيه.
- شغّل: `php artisan test --filter=UsersController` (أو ملف الاختبار الجديد) وتأكّد نجاحه.

## 6) خطوات التحقّق اليدوي
- أنشئ مستخدم اختبار → البريد يصل فعلًا (أو يظهر تنبيه واضح عند الفشل).
- المشرف يسجّل الدخول ويرى اللوحة حسب دوره.
- `failed_jobs` لا يتراكم.

## 7) حلّ فوري مؤقّت (للفريق لحين الإصلاح)
الأدمن يعطي المشرف الإيميل + كلمة المرور التي حدّدها وقت الإنشاء مباشرة (لا حاجة لانتظار البريد).
